# Security policy and threat model

> **Document control:** SEC-001 · Active reference · Custodian: Repository maintainer

## Purpose and scope

This document sets repository-level security practices for source code,
configuration, CI, deployment support, and research artifacts. It is a
practical policy for this research repository, not a security certification or
a claim of compliance with an agency standard.

## Assets and boundaries

Assets include source and workflow integrity; GitHub and host credentials;
self-hosted runner configuration; training-host access; checkpoints, replay
data, and logs; the external game server; dependency and ROM provenance; and
captured frames or other data that may reveal private information.

The [CI operations guide](../operations/ops-001-ci-setup.md) describes the
current hosted and self-hosted runner arrangement. Pull request code executes
on a GitHub-hosted runner in the documented workflow. The self-hosted runner
has access to more valuable host resources and is restricted to the private
repository by current operating practice. The game server may be reached over
the local network or tailnet as described in
[OPS-002](../operations/ops-002-game-server.md). These boundaries are
operational assumptions and must be rechecked when workflows or deployments
change.

## Required handling

- Never commit passwords, tokens, private keys, tailnet credentials, RCON
  credentials, or other secrets. Keep runner environment files outside the
  repository with access limited to the service account; rotate credentials
  promptly if exposure is suspected.
- Keep untrusted pull request code on hosted runners. Do not attach a
  self-hosted runner to a public repository or run unreviewed code on a host
  holding deployment credentials or unique research state.
- Give workflows only the permissions they need. Review triggers, checkout
  behavior, third-party actions, and dependency changes before expanding
  access.
- Obtain dependencies and game assets from documented sources, preserve
  checksums where available, and review applicable licenses before
  redistribution.
- Review logs, frames, captures, and experiment artifacts for credentials or
  private data before sharing them outside the repository.
- Follow the recovery and backup practices in
  [OPS-005](../operations/ops-005-operations.md); a backup is not verified
  until restoration has been checked.

## Reporting a vulnerability

Do not publish exploit details or credentials in a public issue. Use GitHub's
private vulnerability reporting feature if it is enabled for this repository.
Otherwise, contact the repository maintainer privately through an established
repository-owner channel. Do not include live secrets in the initial report.

The maintainer should acknowledge and triage the report, identify affected
code and deployments, contain exposure (including credential rotation where
appropriate), prepare and verify a correction, and coordinate disclosure with
the reporter. No response-time guarantee is currently established.

## Incident response and review

For suspected exposure, revoke or rotate affected credentials first, then
identify affected commits, workflow runs, hosts, and artifacts. Preserve
relevant logs where safe, remove exposed copies where possible, and record the
incident and corrective action in the repository's operational records.
History rewriting does not replace credential rotation.

Review this policy after a security incident, a material workflow or host
change, or a change to secret handling. The current CI limitations and manual
operating steps are recorded in [OPS-001](../operations/ops-001-ci-setup.md);
in particular, manual dispatch and deployment workflows require deliberate
operator review. This policy does not assert that every deployment is hardened
or that the repository meets NIST or other compliance requirements.
