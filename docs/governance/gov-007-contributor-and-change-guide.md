# Contributor and change guide

> **Document control:** GOV-007 · Active reference · Custodian: Repository maintainer

## Purpose

This guide explains how to make changes that preserve the repository's
research claims, operational safety, and document history. It is the
repository's contribution guidance; it intentionally lives in the controlled
documentation collection rather than a root `CONTRIBUTING.md`.

## Before changing code or configuration

1. Read the relevant architecture and operations documents from the
   [documentation index](../README.md).
2. Identify the behavioral contract, claim, or operational assumption the
   change touches. Current research claim limits are in
   [GOV-005](gov-005-claims-evidence-register.md).
3. For a durable cross-component decision, follow the
   [decision record process](gov-006-decision-record-process.md).
4. For a planned comparison, freeze the hypothesis, metrics, seeds, and
   failure conditions under the [A/B protocol](../foundation/fnd-001-ab-protocol.md)
   before observing results. Keep result records distinct from the protocol.

## Documentation and code references

Update the controlling documentation when a change alters an interface,
behavioral invariant, reward path, configuration default, deployment step,
security boundary, or evidence claim. Use the document ID and a stable
relative link in code comments for non-obvious invariants. Comments should
explain why the local code must behave a certain way; keep broad rationale,
procedures, and mutable status in the document. Avoid references to line
numbers and duplicated status summaries.

New authored documents follow the naming and registration rules in
[DOC-001](../README.md). Generated records retain their provenance-bearing
names. Update links and indexes in the same change as a move or rename.

## Verification and review

Use the assurance plans and CI workflow that apply to the changed surface.
Documentation-only changes are checked by the repository's documentation
integrity job. This guide does not imply a multi-person review process; the
repository is maintained by its current maintainer, who should record material
limitations and unresolved validation explicitly.

## Security and artifacts

Follow [SEC-001](../security/sec-001-security-policy.md) for secrets, workflow
permissions, and vulnerability reports. Do not commit credentials. Before
publishing research artifacts, review them for private data and retain the
protocol, hashes, seeds, and provenance needed to interpret the result.
