# Evaluator state is not a learning input

> **Document control:** ADR-002 · Accepted · Custodian: Repository maintainer

**Decision source:** User-fixed design decisions recorded in ARC-004, section
2, on 2026-10-11. This record transcribes that decision; it is not a new
approval.

## Context

Game engines can expose state that a player cannot observe, such as object
lists, map coordinates, internal memory reads, or score variables. Such data
can make evaluation easier while invalidating the claim that behavior was
learned from player-facing experience.

## Decision

Keep privileged engine state in the red evaluator channel. It may support
scoring, diagnostics, or evaluation, but must not enter the policy, world
model, training targets, or reward path as a learning signal. The player earns
rewards through the ordinary game interaction. ARC-004 defines the game
adapter boundary and source design.

## Consequences and limits

Adapters must make the evaluator/learning boundary explicit and reviewable.
Tests and audits should guard this boundary as implementations evolve. A
separate evaluator channel does not by itself prove that all information flow
is isolated; behavior across games remains subject to the evidence gates in
ARC-004 and [GOV-005](../governance/gov-005-claims-evidence-register.md).

## Alternatives recorded in the source design

Using privileged state to guide learning was rejected because it would
confound player learning with engine access. See ARC-004 for the original
decision context.
