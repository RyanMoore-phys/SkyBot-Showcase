# Order of response when a change needs more compute

> **Document control:** ADR-005 · Accepted · Custodian: Repository maintainer

**Decision source:** the owner, 2026-10-20, in the working session that opened
[GOV-008](../governance/gov-008-human-like-learning-motivation.md). This record
transcribes that instruction.

## Context

The training host has 8 GB of GPU memory and 16 GB of RAM. Several candidate
changes in GOV-008 (decision-time planning, attention, consolidation, per-stream
reward terms) add compute or memory. Some rule is needed for what gives way, so
that a change is judged on what it adds and not on an ad hoc cut elsewhere.

## Decision

When a change needs more compute or memory than is available, reduce in this
order:

1. **Model size**, down the size ladder.
2. If the model is **at saturation** (no further reduction is possible, or
   a reduction fails the quality tolerance), **reduce the number of streams**.
3. If the number of streams is **low**, **slow the stepping rate**.

## Consequences and limits

- The thresholds "saturation" and "low" are **not defined** by this record. They
  must be defined, with numbers, in the implementation plan before the rule is
  applied.
- The order interacts with measured behaviour. Fewer streams means less
  experience per hour; slower stepping changes how much game time each decision
  covers in a real-time game; and the existing autoscaler's rules (including its
  response to memorising) were written before this order and will need to be
  reconciled with it.
- Evaluation runs fix their configuration in their protocol
  ([ASS-007](../assurance/ass-007-adaptability-evaluation-protocol.md)); the
  order applies to development, not to a frozen comparison.
- This is an owner decision, not an optimisation proven to be best. If a result
  shows another order is better, a superseding record is added.

## Amendment 1 (2026-10-20, assistant determination under the owner's delegation)

The owner left the thresholds undefined and allowed the assistant to determine
unanswered points consistently with the owner's directive. These definitions are
**provisional**: they are to be confirmed by measurement in the implementation
plan and may be overruled by the owner.

- **Model at saturation:** the model is at the smallest rung of the size ladder,
  or the next smaller rung fails the quality tolerance (fresh-data loss more than
  10 % worse than the current model's on the same held-out windows, the same
  tolerance the existing shrink tool uses).
- **Streams are low:** at or below half of the maximum stream count (four of
  eight).
- **Slower stepping** is the last resort, and any slowing is logged with the
  amount of game time per decision it implies in a real-time game.

## Amendment 2 (2026-10-21, response to the branch audit)

Source: [ASS-009](../assurance/ass-009-audit-response-adjustments-branch.md), finding
3.9. The assistant's judgement; revisable by the owner.

- **Both arms of a comparison always run the same configuration.** If a change needs a
  reduced configuration (a smaller model, fewer streams, slower stepping), the
  reduction is applied to the baseline arm too, so the comparison is *baseline at the
  reduced configuration* against *baseline plus change at the reduced configuration*.
- **The reduction is itself recorded as a tested difference.** A separate record states
  the cost of the reduction (promoted baseline at the full configuration against at the
  reduced one) so the price of the compute decision is visible, not hidden in the
  change's result.
- **How the "10 % worse" tolerance is measured.** Fresh-data loss on the same held-out
  windows at the same step budget, **plus** the mechanism measures (state dependence,
  action attribution) and a retention probe. A reduction fails the tolerance if any of
  them regresses beyond the A/A noise floor, not only the loss.
- **Frozen evaluation runs** keep their protocol configuration; the rule applies to
  development only.
